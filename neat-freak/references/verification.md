# 什么结论要什么证据

## 结论越重，证据越硬

| 你要下的结论 | 最低证据 |
|---|---|
| 文档链接有效 | 项目自己的链接或索引检查通过，或者逐个确认目标存在 |
| 两份规则文件同源 | 软链或导入确实指向同一份，并且平台实际加载到了 |
| 代码实现是 X | 目标分支上现在的代码、schema、配置和相关测试 |
| PR 已完成 | PR 状态是已合并，有合并提交。这推不出已部署 |
| 已部署 | 部署记录或线上的版本标记指向这次提交，服务在运行 |
| 用户已经看到新版本 | 用户实际访问的地址或接口返回了新内容 |
| 可以清场 | 已合并，线上包含这次改动，文档和规则已同步，工作区没有未提交内容，要删的东西里没有别处找不到的独有内容 |
| 已获准清场 | 用户在这次任务里明确让你清理，而且要删的对象在他说的范围内 |
| 整个项目干净 | 适用的每一面都核实过；未核实的、范围外的单独列出 |

对代码的印象、旧记忆、提交说明、加了防缓存参数的网址，都只能当线索，证明不了线上的状态。

## 发布走到了哪一步

一次改动从写完到收尾依次是：

写完并本地验证 → 推送或开 PR → 检查通过 → 合并 → 部署 → 线上验证 → 文档、规则和记忆同步 → 清理分支、工作树和临时产物 → 清理后再查一遍

卡在哪一步，就按那一步汇报，不用「基本完成」盖过去。跳过某一步要有项目规则允许的理由。

项目没有部署环节（本地工具、还没上线的小项目）时，后面几步不适用，如实说不适用，不编造部署状态。

## 内容经过缓存或有多个出口时

用户看到的内容经过 CDN、边缘缓存、搜索索引、后台任务或多个客户端时，分开确认：

- 源站是不是新内容；
- 用户实际访问的地址是不是还在返回旧缓存；
- 页面、接口、通知、RSS 是不是同一个数据出口；
- 版本标记是不是在所有后台进程都切换之后才写的。

加防缓存参数只能用来诊断，不能当成用户已经看到的证据。只验证了其中一个出口，就在结论里写明只验证了哪个。

## 清场之前

1. 确认这次的工作已经合并并上线；
2. 文档、规则和允许维护的记忆已经同步；项目规则要求留收尾记录的，留好；
3. 列出要删的工作树、分支、临时库和中间产物；
4. 检查里面有没有未提交的文件，有没有别处找不到的内容；
5. 核对用户在这次任务里的清理授权。已经明确批准的不再问；
6. 清理授权范围内的对象。还有独有内容的、没获授权的保留下来，写进待决；
7. 清理后重新查一遍工作区，汇报实际删了什么、还剩什么。

目录名、分支多旧、Agent 会话是否已关闭，都不能证明可以删。

## 验证失败时

- 同一个失败出现第二次，停止盲目重试，回头检查假设、环境和命令名。
- 检查要求机器可读的记录时，补上正确的记录再触发一次。能修的格式问题不用人工确认绕过去。
- 失败发生在写入生产之前，明确说「还没有影响生产」。发生在切换之后，先确认现在线上跑的是哪个版本、能退回到哪。
- 没核实的保持「未核实」，不为了让摘要好看而降成一句提醒。
